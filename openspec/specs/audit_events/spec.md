# Audit Events Specification

## Purpose

The `audit_events` bounded context is the append-only, synchronous audit log of domain write events. The table is the one defined in `docs/modelo-de-datos-proyecto-04.md` §3.9, materialized by migration `00011_create_audit_events.sql`. This slice delivers the table, the domain entity (`AuditEvent` + `ActorType` VO + event-type constants), and a single append operation; there is no read surface, no outbox / SNS / SQS / EventBridge fan-out, and no UPDATE/DELETE path by construction. Every event is appended in the same database transaction as the domain write that produced it (co-write atomicity — see `Co-Write Atomicity Contract` and the applications delta's `Fail-Closed Application + Audit Co-Write`). The audit log survives its actors: `actor_id` has no foreign key. Exactly four event types are emitted in this cycle: `ApplicationSubmitted` and `ApplicationTransitioned` from the `applications` write paths; `CompanyUpdated` and `CompanyDeleted` from the `companies` owner-only write paths. The jobs and identity write paths emit nothing. `event_type` is deliberately NOT CHECK-constrained (§1.3 exception — event types grow constantly); the closed set for this cycle is enforced at the application layer, not the DB.

## Requirements

### Requirement: Audit Events Schema Migration

Migration `00011_create_audit_events.sql` MUST create the `audit_events` table exactly as `docs/modelo-de-datos-proyecto-04.md` §3.9 defines it: `id UUID PRIMARY KEY` (no DB default — the id is generated by the emitting write path); `occurred_at TIMESTAMPTZ NOT NULL DEFAULT now()`; `actor_id UUID NULL` (MUST have NO foreign key — the audit log survives its actors); `actor_type TEXT NOT NULL` constrained by `audit_events_actor_type_check` to `'user'|'system'`; `event_type TEXT NOT NULL` (MUST have NO CHECK constraint — the §1.3 exception); `entity_type TEXT NOT NULL`; `entity_id UUID NOT NULL`; `metadata JSONB NOT NULL DEFAULT '{}'`. The migration MUST also create the B-tree index `audit_events_entity_idx` on `(entity_type, entity_id, occurred_at DESC)`. The table MUST have NO `updated_at` column and NO `deleted_at` column. `goose down` MUST drop the table and the index (clean drop — no other table references `audit_events`).

#### Scenario: up creates named objects

- GIVEN the DB at migration `00010`
- WHEN `goose up` runs `00011`
- THEN `audit_events`, the `audit_events_actor_type_check` CHECK, and the `audit_events_entity_idx` index exist

#### Scenario: down drops table and index

- GIVEN `00011` applied
- WHEN `goose down` runs
- THEN `audit_events` and `audit_events_entity_idx` are gone (clean drop; no other migration affected)

#### Scenario: required fields reject NULL

- GIVEN the `audit_events` table
- WHEN an INSERT with `actor_type = NULL` OR `event_type = NULL` OR `entity_type = NULL` OR `entity_id = NULL` is attempted
- THEN the DB rejects the row

#### Scenario: metadata defaults to an empty JSONB object

- GIVEN the `audit_events` table
- WHEN a row is inserted with `metadata` omitted
- THEN the persisted row has `metadata = '{}'` (the `NOT NULL DEFAULT '{}'` default applies)

#### Scenario: event_type is not CHECK-constrained

- GIVEN the `audit_events` table
- WHEN an INSERT with `event_type='SomeFutureEventType'` is attempted
- THEN the DB accepts the row (no CHECK on `event_type` — the §1.3 exception; the closed vocabulary is enforced at the application layer, not the DB)

#### Scenario: the table is structurally append-only

- GIVEN the `audit_events` schema
- WHEN it is inspected
- THEN there is no `updated_at` column, no `deleted_at` column, no foreign key on `actor_id`, and `audit_events_entity_idx` covers `(entity_type, entity_id, occurred_at DESC)`

### Requirement: Actor Type Vocabulary

`actor_type` MUST be closed to exactly `'user'` and `'system'`, enforced by the `audit_events_actor_type_check` CHECK at the DB boundary and mirrored by the domain `ActorType` value object. `'user'` means the actor is a real `users.id` recorded in `actor_id`; `'system'` means the event was produced by system machinery with `actor_id = NULL`. The DB MUST NOT accept any other value.

#### Scenario: user and system are the only accepted values

- GIVEN the `audit_events` table
- WHEN `actor_type` is set to `'user'` or `'system'`
- THEN the DB accepts the row

#### Scenario: out-of-vocabulary actor_type is rejected

- GIVEN the `audit_events` table
- WHEN an INSERT with `actor_type='service'` is attempted
- THEN the DB rejects the row with a CHECK violation (closed vocabulary enforced at the DB boundary)

### Requirement: Event Type Vocabulary (Closed Set for This Cycle)

The `audit_events` domain in this slice MUST expose exactly four event-type constants: `ApplicationSubmitted` and `ApplicationTransitioned` from the `applications` write paths, plus `CompanyUpdated` and `CompanyDeleted` from the `companies` owner-only write paths. No other emit call MAY exist anywhere in the codebase this cycle (the jobs and identity write paths emit nothing). The closure is enforced at the application layer via the typed constants — `event_type` deliberately has no DB CHECK (§1.3 exception), so adding an event type in a future cycle is a code change, not a migration. The two new literals MUST live in the same domain package (`audit_events/domain/entities/auditEvent.go`) so the AST guard `TestEventVocabularyIsClosed` continues to enforce "no emit call site outside this package". The companion `entity_type` for the two new events MUST be the singular string `"company"` (sibling to the singular `"application"` already in use).

#### Scenario: exactly four event-type constants exist this cycle

- GIVEN the `audit_events` domain in this slice
- WHEN its event-type surface is inspected
- THEN exactly `ApplicationSubmitted`, `ApplicationTransitioned`, `CompanyUpdated`, and `CompanyDeleted` exist, and no other event emission call exists in the codebase (the AST guard in `auditEvent_test.go::TestEventVocabularyIsClosed` enumerates the closed set; the emit-literal walk continues to pass because the two new literals stay in the entities package)

#### Scenario: the closed set omits jobs and identity event types

- GIVEN the four-event closed set for this cycle
- WHEN the codebase is scanned for any other `audit_events` emit call (insert into the table or call to `AuditEventRepository.Append`)
- THEN none exists outside the four constants above — the jobs write paths and the identity write paths still emit nothing, even after the vocabulary expansion

#### Scenario: the DB accepts a novel event_type string

- GIVEN the `audit_events` table
- WHEN an INSERT with `event_type='SomeFutureEventType'` (not emitted by this slice) is attempted directly
- THEN the DB accepts the row (no CHECK constraint — the closed set is a code-level invariant, not a DB-level one)

### Requirement: Append-Only Port

The `audit_events` repository port MUST expose exactly one operation: append (record/insert) of an `AuditEvent`. The port MUST have NO update, delete, read, list, or backfill method — the enforcement is absence of surface: no `UPDATE`, `DELETE`, or `SELECT` on `audit_events` exists in this slice's query set, and no caller can mutate or read an appended event through the port.

#### Scenario: the port exposes append only

- GIVEN the `audit_events` repository port in this slice
- WHEN its method surface is inspected
- THEN it exposes exactly one append operation and no `Update`, `Delete`, `Read`, `List`, or `Backfill` method exists (no mutation/read surface by construction)

#### Scenario: the slice's query file contains only the INSERT

- GIVEN the sqlc query source for `audit_events` in this slice
- WHEN it is inspected
- THEN it contains only the append INSERT (no `UPDATE`, `DELETE`, or `SELECT` on `audit_events`)

### Requirement: Co-Write Atomicity Contract

The append operation MUST execute inside the same database transaction as the domain write that produced the event (tx-scoped — the port MUST NOT begin or commit a transaction of its own). If the audit INSERT fails, the transaction MUST be aborted and the caller's domain write MUST roll back with it (fail-closed — no write without its audit trail). The append MUST NOT be performed outside a caller-owned transaction.

#### Scenario: the append runs inside the caller's transaction

- GIVEN a domain write path (apply or transition) that produces an audit event
- WHEN the append port is invoked
- THEN the audit INSERT executes within the same database transaction as the domain write (never a standalone commit)

#### Scenario: an append failure rolls back the caller's write

- GIVEN the audit INSERT fails inside the co-write transaction
- WHEN the transaction is aborted
- THEN no `audit_events` row exists AND the caller's domain write is rolled back too (fail-closed — the event and the write are atomic)

### Requirement: Metadata Shape (PII-Free)

The `metadata` JSONB MUST be built from a fixed, minimal field set and MUST NEVER carry `cover_letter`, candidate PII, or company profile PII. The shape per event type: `ApplicationSubmitted` → `{ "job_id", "source" }` (`job_id` always present; `source` present only when the application row's `source` is non-NULL); `ApplicationTransitioned` → `{ "job_id", "from_status", "to_status" }` (all three always present); `CompanyUpdated` → `{}` (an empty JSON object — the `200 OK` wire body already carries the post-write state, so a "what changed" diff would be redundant and would leak free-text profile values like `name`, `description`, or `website`); `CompanyDeleted` → `{ "jobs_closed" }` (the integer rowcount of the inline `CloseCompanyJobs` UPDATE stringified via `strconv.Itoa`; the `jobs_closed` key is ALWAYS present, even when the rowcount is `0`, so the metadata shape is stable and machine-parseable). The closed-key vocabulary for any application event is `{job_id, source, from_status, to_status}` only; the closed-key vocabulary for any company event is `{jobs_closed}` only; no event in any family MAY carry any other key. A unit test MUST pin the exact allowed per-family key set — including the empty-object invariant for `CompanyUpdated` — so a future edit cannot leak PII into the JSONB, cannot add a profile field to `CompanyUpdated`, and cannot drop the `jobs_closed` key from `CompanyDeleted`.

#### Scenario: ApplicationSubmitted metadata carries job_id and source

- GIVEN an `ApplicationSubmitted` event for job J whose application row has `source='linkedin'`
- WHEN the event is persisted
- THEN `metadata` is exactly `{"job_id": J, "source": "linkedin"}`

#### Scenario: ApplicationTransitioned metadata carries the transition

- GIVEN an `ApplicationTransitioned` event for job J moving an application from `submitted` to `in_review`
- WHEN the event is persisted
- THEN `metadata` is exactly `{"job_id": J, "from_status": "submitted", "to_status": "in_review"}`

#### Scenario: CompanyUpdated metadata is the empty object

- GIVEN a successful `PATCH /me/company` that produced a `CompanyUpdated` event for company C
- WHEN the event is persisted
- THEN `metadata` is exactly `{}` (no diff, no field echoes, no profile PII — the `200 OK` body already carries the post-write state, and the closed-vocabulary unit test pins the empty object as the only allowed value)

#### Scenario: CompanyDeleted metadata carries jobs_closed as a string

- GIVEN a successful `DELETE /me/company` for company C whose inline `CloseCompanyJobs` UPDATE affected N rows (`N` ≥ `0`)
- WHEN the `CompanyDeleted` event is persisted
- THEN `metadata` is exactly `{"jobs_closed": "<N>"}` where `<N>` is the string form (`strconv.Itoa`) of the integer rowcount returned by the adapter

#### Scenario: CompanyDeleted metadata always carries jobs_closed, even when zero

- GIVEN a successful `DELETE /me/company` for company C whose inline `CloseCompanyJobs` UPDATE affected `0` rows (the legitimate "company had no non-closed jobs at delete time" success path — no `draft` or `published` jobs of `C` survived the `IN ('draft','published')` predicate)
- WHEN the `CompanyDeleted` event is persisted
- THEN `metadata` is exactly `{"jobs_closed": "0"}` (the key is present even when the rowcount is zero — stable shape so consumers can rely on a fixed schema rather than a present-or-absent branch)

#### Scenario: cover_letter, candidate PII, and company profile PII never enter metadata

- GIVEN any audit event emitted by the four write paths in scope, including applies that supplied a `cover_letter` and company PATCHes that supplied a new `name`, `description`, or `website`
- WHEN the persisted `metadata` is inspected
- THEN it contains no `cover_letter` key, no candidate PII, and no company profile field (`name`, `description`, `website`, `logo_url`, `size`, `founded_year`, `city`, `country`, `linkedin_url`, `instagram_url`, `facebook_url`, `twitter_url`, `cover_image_url`, `rfc`, `industry_id`) — a unit test pins the per-event-family allowed key set (`{job_id, source, from_status, to_status}` for applications; `{jobs_closed}` for companies; empty object for `CompanyUpdated`)
