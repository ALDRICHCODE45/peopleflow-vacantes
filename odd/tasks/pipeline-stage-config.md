# Pipeline stage configuration (cut 1)
Let the recruiter configure the columns of a draft vacancy's pipeline: rename every stage, reorder between Nuevos and Placement, add up to 3 custom columns and remove them.
Branch feat/pipeline-stage-config from main a39e5ca. Frontend only; the backend session (01a1420b-ba06-7632) implements the endpoints on feat/pipeline-config. Contract: docs/pipeline-customization-design.md at 945d306 (read with `git show 945d306:docs/pipeline-customization-design.md`).

## Specs
- S1. User: «NO hermano, el backend te va a contactar para iniciar algo nuevo, (no se si se debera hacer en la rama en la que estamos, creo que no), recuerda siempre que debes seguir las reglas de diseno que tenemos y priorizar shadcn.» All UI follows docs/frontend-ui-design-rules.md and is built primarily from shadcn components in frontend/src/components/ui. New branch, not feat/draft-list-and-reopen.
- S2. Placement (user choice, 2026-10-15): «En la página del pipeline (recomendado)» — /empresa/vacantes/{id}/pipeline stops showing «no hay pipeline» for drafts and shows the editable columns; reached from the row «Acciones» menu and from the draft editor. Not a draft editor step. The first GET happens when that page opens.
- S3. Product decisions relayed by the backend (user answers): «Q1: las columnas base no se eliminan, solo se renombran y reordenan.» «Q2: los nombres son únicos dentro de la vacante.» «Q3: Nuevos va siempre primera.»
- S4. Contract GET `/v2/me/company/job-drafts/{draftId}/pipeline` → 200 `{"version": decimal string ("0" = defaults never saved), "stages":[{"id":uuid,"kind":"new"|"screening"|"screening_ok"|"in_process"|"placement"|"custom","name":string}], "exit":{"id":uuid,"kind":"discarded","name":string}, "limits":{"maxCustomStages":3,"nameMaxLength":40}}` + strong opaque pipeline `ETag` (never built by the client, never equal to a draft tag). Pure GET; built-in ids deterministic. Unknown kind → invalid response.
- S5. Contract PUT same path, `If-Match` required, body exactly `{"stages":[{"id"?,"name"}],"exit":{"id","name"}}` (no kind; id-less entry = new custom; removed custom omitted; unknown keys rejected) → 200 same body shape in request order with server ids for new custom stages + new ETag. No-op PUT returns the same version. Uncertain PUT is not retried: reconcile with GET. No Idempotency-Key.
- S6. Invariants (validated client-side before sending): exactly one of each built-in kind, built-ins never removed; `new` first and `placement` last in the progression, everything between freely reorderable; `discarded` only in exit; at most `limits.maxCustomStages` custom; names: NFC → trim + collapse Unicode White_Space (incl. NBSP) to one ASCII space, non-whitespace control characters rejected, format characters kept, 1–`limits.nameMaxLength` code points; names unique across progression and exit on the full-Unicode casefold of the normalized name, accents preserved (`Área` = `ÁREA`, `Area` ≠ `Área`). Descartados is renameable.
- S7. Errors `{error, code}` without details: 400 invalid_request, 400 validation_error (shown as a generic failure keeping the edited state), 401, 403 forbidden / company_inactive, 404 not_found (missing, foreign or non-principal draft), 409 company_not_active, 412 version_conflict (no data), 413 payload_too_large, 428 precondition_required, 500 internal_error. Every response no-store.
- S8. PIPE-10: renaming a stage with a critical action (`in_process`, `placement`, `discarded`) requires a dialog explaining that the action remains unchanged. Colors derive from kind client-side; custom stages neutral. Reorder with accessible up/down buttons, Nuevos and Placement fixed.
- S9. Same safety rules as the draft save path: server-only client, Bearer only, redirect "error", strict decoders, no automatic mutation retries, no false success, results through notifyActionResult + ActionStatusSlot (no layout shift).
- S10. User browser test (2026-10-15): «bien, hermano, lo estoy probando y mira: [dos capturas] esta es la ui en modo oscuro y modo claro, y hay algunas modificaciones que haria, en primera, la funcionalidad esta perfecta, funciona como deberia y no hay problema, pero en modo oscuro no se ve muy bien, no se si lo notas, y me gusta la forma en la que puedes cambiar de posicion las columnas, pero me gustaria que puedieras hacer drag and drop tambien, me explico? y algo extra que no se si lo tenias configurado.. es que esta pantalla es mas parecida a una pantalla de CONFIGURACION, no la pantlla del pipeline en si (si me equivoco, dimelo) es decir, segun yo, antes, se tenia una pantlla en la que aparecia un mensaje que decia que el pipeline no se puede visualizar porque la vacante era un borrador, lo que me gustaria es que haya un apartado de "configuracion" en alguna parte para poder ingresar a esta pantalla, me explico? pero bueno, si quieres esto podemos verlo despues, no ahorita, pero si me interesa que lo tengas en mente, no se si me sigues?» Functionality accepted. Dark mode must read well (position medallion and row surfaces). Columns can also be reordered by drag and drop, keeping the up/down buttons. Deferred, not now: the editor is a configuration screen; the pipeline page should go back to the «no pipeline because it is a draft» message and the editor should live in a «Configuración» section reached from somewhere.
