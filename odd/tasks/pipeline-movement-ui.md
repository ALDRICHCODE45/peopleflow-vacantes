## Specs
- S1. User standing instructions: keep implementing while away and queue what to review; follow docs/frontend-ui-design-rules.md and shadcn first (never edit components/ui/*, never install packages); audit against §9; add learned patterns to the rules; test-first; strict decoders; no automatic retries.
- S2. User decisions (§12.6): «forward one stage at a time; backward to any earlier stage.» «coverage counting (covered of headcount) is in this cut.» «candidates see «Enviada» in `Nuevos` and «En proceso» elsewhere.» «one candidate per move; no bulk moves.» «while a vacancy has candidates, columns can only be renamed until cut 7.»
- S3. Board GET `/v2/me/company/job-drafts/{vacancyId}/board` → {stages:[{id, kind, name, count}], exit:{id, kind:"discarded", name, count}, coverage:{covered, required|null, full_coverage_reached_at|null}, participations:[{id, stage_id, version, etag, candidate:{id, full_name}, applied_at, source:"organic", cv:{id,name}, moved_at}]}; stage kinds `new | screening | screening_ok | in_process | placement | custom`; errors 422 board_too_large, 409 vacancy_not_published, 404 not_found. `required: null` = headcount not set → «X plazas cubiertas» without «de Y»; otherwise «X de Y plazas cubiertas».
- S4. Move POST `…/participations/{participationId}/moves`, `If-Match` = the item's `etag` sent unchanged (never built from `version`, which is display-only), body exactly `{to_stage_id, confirm_placement_exit?}` → 200 moved item (with new `etag`, also in the ETag header) + `coverage`. Errors: 409 stage_skip_not_allowed, 409 placement_exit_confirmation_required, 400 validation_error, 400 invalid_request, 412 version_conflict, 428 precondition_required, 404 not_found, 409 vacancy_not_published. The client recomputes column counts from the moved item plus coverage; on an uncertain result, 412 or 404 it reloads the board and never retries automatically. `Descartados` is not a move target in this cut (shown read-only).
- S5. UI (§12.4): the board on `/empresa/vacantes/{id}/pipeline` for published vacancies connects to GET board (drag and drop plus a non-pointer move menu); a move to a non-adjacent forward column is disabled in the UI and the server stays the authority; leaving Placement opens a confirmation dialog (then sends confirm_placement_exit: true); coverage «X de Y plazas cubiertas»; a candidate sheet shows the history.
- S6. Candidate sheet data: GET `…/participations/{participationId}` → board item + `screening: [{question_id, prompt, type, answer}]`, answer `{option_id, label}` or `{text}`; no score or correctness shown. GET `…/participations/{participationId}/history` → {items:[{kind: intake|move, from_stage_id|null, to_stage_id, hire, departure, actor:{kind: candidate|recruiter, id, full_name}, at}]} oldest first; stage names from the board. GET `…/participations/{participationId}/cv` → attachment, no-store; 503 cv_storage_unavailable; 404 otherwise — downloaded through a Next Route Handler with the recruiter Bearer server-side (same pattern as the P2b candidate CV download).
- S7. Column editor: GET/PUT `…/pipeline` gain `structure_locked: boolean`; when true the editor disables reorder/add/remove with an explanation and allows only renames; PUT can return 409 stage_change_requires_empty_pipeline (authority; nothing written).
- S8. Candidate side: GET /v2/me/applications `status` becomes `submitted | in_process` (strict); /candidato/postulaciones shows «Enviada» for submitted and «En proceso» for in_process; nothing else about the stage.
