# Candidate CV library and applications P2b (frontend)
Let a signed-in candidate manage a real CV library, apply to a published vacancy with a CV and the screening answers, and see their applications.
Branch feat/candidate-applications-ui stacked on feat/candidate-identity-ui (0658e46); not merged to main until the user's browser review (docs/pending-user-review.md). Frontend only, in parallel with the backend session (01a1420b-ba06-7632) on feat/candidate-applications. Contract: `git show 47fea7d:docs/pipeline-customization-design.md` §10.5, plus the frontend notes in L1.

## Specs
- S1. User standing instructions: keep implementing while away and queue what to review; follow docs/frontend-ui-design-rules.md and shadcn first; audit against §9; add learned patterns to the rules.
- S2. User decisions relayed by the backend: CV mandatory (INT-17), PDF and .docx verified by content, max 5 MB, local storage behind an interface; candidate session required; CV library reused across applications, each application keeps its exact CV version; «Todas las preguntas de filtro son obligatorias; las abiertas aceptan hasta 2.000 caracteres.»; the candidate only sees «Postulación enviada» until cut 4; CVs can be renamed.
- S3. CV library (candidate Bearer): GET /v2/me/cvs → {items:[{id, name, size, content_type, uploaded_at, in_use}], limits:{max_cvs, max_bytes, content_types}} newest first; POST multipart (`file` exactly once, optional `name` 1–120 code points) → 201 cv; errors 413 cv_too_large, 415 cv_unsupported_type, 400 cv_content_mismatch, 409 cv_library_full, 400 invalid_request; no idempotency key (a retried upload may create a duplicate the candidate can delete); PATCH {name} → 200 cv; DELETE → 204 (applications keep their version); GET /v2/me/cvs/{id}/file → attachment.
- S4. Screening GET /v2/jobs/{id}/screening (public) → {questionnaire_revision, questions:[{id, prompt, type: open|single_choice, options: [{id,label}]|null}], limits:{open_answer_max_length}}; 404 for legacy/unpublished; questions may be empty.
- S5. Apply POST /v2/jobs/{id}/applications with Idempotency-Key, body exactly {cv_id, questionnaire_revision, answers:[{question_id, option_id}|{question_id, text}]} → 201 {id, vacancy_id, status:"submitted", applied_at} (replay with the same key returns the original 201). Errors: 404 not_found, 409 already_applied, 409 questionnaire_changed (reload the form), 422 invalid_answers with details [{question_id, reason: required|unknown_option|too_long|wrong_type}] (only envelope with details here; decode strictly), 422 cv_unavailable, 400 invalid_request, 409 idempotency_conflict, 400/428 idempotency-key codes. No automatic retry; uncertain → keep the key and let the user retry explicitly.
- S6. Candidate list GET /v2/me/applications?cursor&limit → {items:[{id, vacancy:{id,title}, company:{id,name}, applied_at, status:"submitted"}], next_cursor}.
- S7. Transport: upload and download go through Next Route Handlers (app/api/…) that forward to the backend with the candidate Bearer resolved server-side; no change to serverActions.bodySizeLimit; never ship the token to the browser.
- S8. UI: /candidato/cvs shows the real library (upload with client-side checks of type/size from limits before sending, rename, delete with confirmation noting applications keep their copy, download, «En uso» badge, limit counter); the public detail of a source=vacancy shows «Postularme» again (hidden in P2a) leading to the vacancy apply flow; the apply flow uses the existing wizard steps (datos → CV → preguntas → resumen) with: choose a library CV or upload one, all screening questions required (open ≤ limit), summary, explicit «Enviar postulación»; success «Postulación enviada»; already applied → state with a link to «Mis postulaciones»; /candidato/postulaciones lists real applications with «Postulación enviada». Not signed in as candidate → the existing identity guard/router.
